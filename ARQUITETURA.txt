1. VISAO GERAL
--------------
Um projeto Firebase (bluezone-d2757, conta contato@abluezone.com.br) concentra tudo:
site, banco, login, backend e, depois, os apps Android e iOS. Nada precisa ser
refeito quando os apps chegarem: eles usam as mesmas Functions, o mesmo banco e as
mesmas regras.

Regra de ouro: o navegador e os apps NUNCA escrevem dados sensiveis direto no banco.
Toda escrita passa pelo backend (Cloud Functions), que valida, limita e registra.

6. ETAPA 3B - PAGAMENTOS (Mercado Pago: Pix, cartao e recorrencia)
------------------------------------------------------------------
Objetivo: vender no proprio site (cursos, assinaturas, produtos) sem depender so da Kiwify.
Pecas:
- Cloud Function "createPayment": cria a preferencia/pedido no Mercado Pago (Checkout Pro ou Checkout
  Transparente para Pix) com o access token guardado no Secret Manager. O navegador NUNCA fala com o
  Mercado Pago com credencial; so recebe o link/QR do Pix.
- Cloud Function "mpWebhook": recebe as notificacoes (pagamento aprovado, recusado, estornado, assinatura
  criada/cancelada), valida a assinatura x-signature do Mercado Pago, consulta a API para confirmar o status
  (nunca confiar so no corpo da notificacao) e grava em Firestore: payments/{id}, subscriptions/{id},
  enrollments (libera o curso) e um "event" na timeline do lead/aluno.
- Recorrencia: "preapproval" (assinaturas) do Mercado Pago para planos mensais; cancelamento e retentativas
  refletidos por webhook; status da assinatura decide o acesso (rules leem enrollments/subscriptions).
- Pix: QR e copia-e-cola gerados pela Function; expiracao curta; confirmacao so por webhook.
Seguranca:
- Idempotencia por id de pagamento/notificacao (deduplicacao persistente), retry seguro, logs de auditoria.
- Reconciliacao diaria (lista de pagamentos do MP x Firestore) para pegar webhook perdido.
- Valores e produtos definidos no servidor (o cliente manda so o id do produto), nunca o preco pelo navegador.
- Dados de cartao nunca passam pelo nosso backend (tokenizacao do MP); LGPD: guardar so o necessario.
- Sandbox do MP para testes; chaves de producao so no Secret Manager; alertas de erro nas Functions.
Depende do plano Blaze (Functions).


7. ETAPA 3C - MARKETING: GOOGLE ADS, META ADS E ANALYTICS
--------------------------------------------------------
Objetivo: medir e otimizar campanhas (trafego pago) com os eventos reais do site: lead, inscricao, compra.
Pecas:
- Google Tag (gtag.js) + Google Analytics 4 + conversoes do Google Ads; Meta Pixel + Conversions API (CAPI).
- Carregamento so depois do consentimento (banner de cookies LGPD com "aceitar", "recusar" e preferencias);
  Consent Mode v2 do Google. Sem consentimento, nada de pixel no navegador.
- Eventos padronizados (mesmos nomes no GA4, Ads e Meta): view_page, lead (formulario/pop-up/newsletter),
  begin_checkout (clique em comprar), purchase (confirmado pelo webhook do Mercado Pago/Kiwify - server-side).
- Envio server-side (CAPI da Meta e Enhanced Conversions do Google) pelas Cloud Functions, com hash dos
  dados (SHA-256 de e-mail/telefone) e deduplicacao por event_id entre navegador e servidor.
- Parametros de campanha (utm_*) e gclid/fbclid guardados no lead (Firestore) para saber a origem de cada
  contato e fechar o funil ate a venda.
Seguranca e privacidade:
- CSP do Hosting liberando so os dominios das tags (googletagmanager.com, google-analytics.com,
  connect.facebook.net, facebook.com) e nada mais.
- Tokens do Ads/Meta so no Secret Manager (Functions); politica de privacidade e cookies publicada;
  consentimento registrado com data/versao; dados pessoais nunca em texto claro nos pixels.
- Painel: aba "campanhas" mostrando origem dos leads (utm/canal) e conversoes por periodo.
Depende do plano Blaze para a parte server-side; o pixel/GA4 com consentimento pode entrar antes.
Feito em 15/09/2026 (lado do site): politica de privacidade em /privacidade, banner de cookies com Consent Mode v2,
carregador de GA4/Ads/Meta/GTM por variaveis VITE_* (vazias = desligado), eventos lead/sign_up/begin_checkout/
view_promotion, utm/gclid/fbclid e consentimento gravados na planilha, CSP liberado. Falta: a cliente criar as
contas (Analytics, Ads, Meta Business, opcional GTM) e colar os IDs; parte server-side (CAPI, Enhanced Conversions).

10. ESCALABILIDADE, DISPONIBILIDADE E OPERACAO
--------------------------------------------
Hospedagem
- Firebase Hosting entrega o site por CDN global com HTTPS automatico; escala sozinho e nao tem servidor
  para cair. Dois sites (prod/teste) + previa no GitHub Pages: nada e publicado em prod sem passar pelo teste.
- Rollback: Hosting guarda versoes; "firebase hosting:rollback" ou pelo console volta em segundos.

Banco (Firestore)
- Serverless e replicado pela regiao (southamerica-east1); escala por leitura/escrita sem ajuste nosso.
- Modelagem para escala: documentos pequenos, consultas por indice (status+publishedAt, slug+status),
  listas paginadas (limit), sem varreduras. Contadores/agregacoes futuras em documentos proprios.
- Regioes: se um dia precisar de multi-regiao, migracao por exportacao/importacao (planejar antes de crescer).

Backend (Cloud Functions, apos Blaze)
- Funcoes pequenas por responsabilidade (submitLead, kiwifyWebhook, mirrorToSheet...), idempotentes
  (chave de deduplicacao por envio/webhook), com retry seguro e timeouts curtos.
- Regiao southamerica-east1, memoria minima; concorrencia da plataforma cuida de picos.

Disponibilidade e recuperacao
- Backups: backup agendado diario do Firestore (recurso nativo), retencao de 7 dias (ativo desde 12/09/2026).
  Exportacoes mensais para o Storage podem entrar depois para retencao longa.
- Recuperacao: procedimento documentado (importar exportacao; republicar versao anterior do Hosting).
- Dependencias externas (Apps Script/planilha, Kiwify): o site nunca quebra se elas falharem -
  mensagens de erro amigaveis e tentativa posterior.

Observabilidade
- Logs das Functions e do Hosting no Google Cloud Logging; alertas de erro por e-mail.
- Orcamento e alertas de custo no faturamento: R$ 50/mes com avisos em 50/90/100% (criado em 12/09/2026).
- Uptime check do dominio (Cloud Monitoring) apos o Blaze.

Ambientes e entrega
- teste (bluezone-teste.web.app, noindex) -> aprovacao -> prod (abluezone.com.br).
- Testes automaticos (unitarios + smoke em navegador) rodam a cada push; build falha bloqueia publicacao.
- Configuracao por variaveis de ambiente (.env local, variaveis do GitHub); nenhum segredo no codigo.


11. GESTAO DE CUSTO (plano)
---------------------------
Ja aplicado (12/09/2026)
- Site estatico em CDN (Hosting): assets versionados com cache de 1 ano; HTML sem cache; nada e processado por visita.
- Site institucional nao carrega o Firebase; so BlueNews e painel usam o banco.
- Firestore: leituras unicas (sem onSnapshot no publico), limit(50), consultas por indice, so publicados; 1 leitura por noticia aberta.
- Imagens reduzidas no navegador (<= 1600px, <= 500 KB) e cache de 1 ano no Storage.
- Formularios via Apps Script (gratuito) com limite de envios e honeypot: ninguem gera custo por formulario.
- Auth na cota gratuita; backup do Firestore com retencao de 7 dias; alerta de orcamento R$ 50 (50/90/100%).

A fazer (sem custo, so codigo), em ordem de impacto

[ ] 2. Cache da lista publicada no navegador (sessionStorage, ~5 min): navegar entre noticias nao gera leituras novas.

[ ] 6. App Check (reCAPTCHA Enterprise) em Firestore e Storage: bloqueia robos usando a config publica para leituras em massa.

Regras permanentes
- Nunca usar escuta em tempo real em pagina publica; sempre paginar; nunca ler colecao inteira.
- Nunca guardar arquivo original grande; sempre comprimir/derivar no envio.
- Toda nova Function nasce com limites (memoria, timeout, retries) e deduplicacao.
- Revisar o painel de uso do Firebase e a fatura no inicio de cada mes.

Aplicacao e rede
- CSP restritiva no Hosting (scripts so do proprio site), HSTS, X-Frame-Options DENY, Referrer-Policy.
- App Check (reCAPTCHA Enterprise) em Firestore, Storage e Functions quando o Blaze estiver ativo.
- Limite de envios por IP/e-mail no servidor; honeypot no site; validacao dupla (cliente + servidor).
- Webhooks (Kiwify) com verificacao de assinatura e deduplicacao.

Segredos e cadeia de entrega
- Segredos so em Secret Manager/config das Functions; .env fora do Git; variaveis publicas do Firebase
  sao publicas por desenho (as regras protegem).
- Dependencias atualizadas (npm audit periodico); GitHub com 2FA; branch main protegida (revisao antes de merge).
- Logs de auditoria: toda acao relevante vira um "event" (quem, quando, o que).

Backups e resposta a incidentes
- Exportacao diaria do Firestore + versoes do Hosting = ponto de retorno.
- Plano de incidente: (1) despublicar/rollback, (2) revogar chaves/sessoes, (3) corrigir, (4) comunicar.
